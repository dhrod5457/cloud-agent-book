# Phase 7 전체 초고 편집/교정 계획

## 목적

Phase 6에서 작성한 1~18장 초고를 출판 가능한 흐름으로 정리한다.

이 단계에서는 새 개념을 늘리지 않는다.

우선순위는 다음과 같다.

```text
중복 압축
→ 용어 통일
→ 장간 연결
→ 예제 정리
→ 수치/근거 구분
→ 문장 교정
```

책의 중심 질문은 그대로 유지한다.

> 이 Task는 Local에서 해야 하는가, Cloud로 보내야 하는가?

---

# 편집 원칙

## 1. 최초 설명 장에 개념을 남긴다

같은 개념이 여러 장에 반복되면 최초 설명 장에서 정의하고 후속 장에서는 적용만 다룬다.

대표 구간:

```text
2 ↔ 5 ↔ 17
3 ↔ 8 ↔ 10
4 ↔ 12
7 ↔ 16
13 ↔ 15 ↔ 16
```

## 2. 핵심 문장은 Part 기준점으로만 반복한다

다음 문장은 책 전체의 기준 문장으로 유지하되 연속 장마다 다시 길게 설명하지 않는다.

- Cloud Agent는 Local Agent를 대체하지 않는다.
- Cloud Agent의 핵심 가치는 더 많은 Token이 아니라 독립 실행환경과 병렬성이다.
- CPU에는 일을 많이 시키고, LLM에는 필요한 정보만 보여준다.
- Runner가 할 수 있으면 Runner에게 맡긴다.
- 작은 Task와 작은 Context를 전달한다.
- Agent에게 개발환경을 설치하게 하지 말고 바로 작업 가능한 환경을 제공한다.
- Cloud Agent에게 결과를 요구하지 말고 검증 가능한 결과물을 요구한다.
- 병렬화의 대상은 Agent가 아니라 독립 Task다.

## 3. 용어 표기

다음 표기를 기본으로 사용한다.

```text
Cloud Agent
Cloud Runner
Local Agent
Task
Task Contract
Prepared Environment
Result Gateway
Evidence
Artifact
Human Steering
Developer Blocking Time
Local Fallback
```

한 문단 안에서 같은 개념을 여러 한글/영문 표현으로 바꾸지 않는다.

## 4. 설명용 수치는 예시라고 밝힌다

다음 유형의 숫자는 실제 제품/프로젝트 수치처럼 보이지 않게 한다.

- 테스트 건수
- Build/Test 시간
- Retry 횟수
- Agent 수
- PR 처리량
- Cloud 준비시간

공식 자료나 측정값이 필요한 경우 `research/`에 기준일과 출처를 남긴다.

## 5. 반복 예제는 연결 장치로 사용한다

`AuthService expired token`, `AUTH-142`, `expected 401 / actual 200` 예제는 책 전체의 연결 예제로 유지한다.

다만 같은 배경을 매 장 처음부터 설명하지 않는다.

후속 장에서는 다음처럼 앞 장의 상태에서 시작한다.

```text
7장에서 만든 AUTH-142 Task Contract를 그대로 사용한다.
```

## 6. 장간 참조는 현재 18장 목차만 사용한다

과거 22~23장 체계나 폐기된 장 번호를 사용하지 않는다.

주요 연결:

```text
7 → 8
8 → 10
9 → 10
10 → 11
12 → 13
13 → 14
15 → 16
17 → 18
```

## 7. 제품 사례는 원칙보다 앞에 두지 않는다

제품명은 원칙을 설명하는 현재 사례로만 사용한다.

변경 가능한 항목은 본문 핵심 규칙으로 만들지 않는다.

```text
CPU / RAM / Disk
동시 Session 수
가격
Rate Limit
UI
제품별 제한
```

## 8. 문체

- 빈 서론과 반복 결론을 줄인다.
- 한 문단에 하나의 판단만 둔다.
- 긴 문장은 둘로 나눈다.
- 과장 표현을 쓰지 않는다.
- 자연어 주장 뒤에는 가능한 경우 실행 구조나 Evidence를 붙인다.
- 같은 의미의 문장을 바로 다음 문단에서 다시 말하지 않는다.

# 장별 편집 초점

## 1~4장

- 정의와 가치만 남긴다.
- 뒤 장의 Task Contract, Result Gateway, Runner 상세를 미리 설명하지 않는다.
- 1장 제품 사례는 공식 근거가 있는 범위만 유지한다.

## 5~6장

- 5장은 판단 Framework, 6장은 작업 Catalog로 분리한다.
- 동일 작업 예시를 두 장에서 장황하게 반복하지 않는다.

## 7~8장

- Input과 Output의 대칭 구조를 살린다.
- JSON/로그 예제는 필요한 수준만 남긴다.

## 9~10장

- 9장은 준비 비용, 10장은 실행 경로에 집중한다.
- Runner 정의를 여러 절에서 반복하지 않는다.

## 11~12장

- 11장은 격리 조건, 12장은 병렬화 비용과 상한에 집중한다.
- Git 입문 설명은 하지 않는다.

## 13~14장

- 13장은 Human-driven Handoff, 14장은 Event-driven Handoff로 분리한다.

## 15~16장

- 15장은 운영 모델의 정적 구조.
- 16장은 하나의 기능이 이동하는 시간 순서.
- 1~14장 개념을 다시 정의하지 않고 적용한다.

## 17장

- 5장의 반대편 판단으로 정리한다.
- Cloud를 쓰지 않는 결정을 실패처럼 표현하지 않는다.

## 18장

- 현재 책의 결론을 먼저 닫는다.
- Harness/Orchestration은 다음 단계로만 소개한다.
- Agent Platform 일반론으로 확장하지 않는다.

# 완료 조건

Phase 7 완료 조건:

- 1~18장 편집본 반영
- 장간 중복 압축
- 용어 표기 통일
- 과거 장 번호 참조 제거
- 설명용 수치 표기 점검
- 제품 사례 출처 점검
- Part 전환부 점검
- 전체 흐름 최종 독서

편집 후에도 책의 최종 독자 판단은 바뀌지 않는다.

> 이 작업은 Local에서 하고, 이 작업은 Cloud Agent에게 보내자.
