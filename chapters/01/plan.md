# 1장 설계 - 개발자가 코드를 작성하던 프로젝트에서 Agent가 작업하는 프로젝트로

## 장의 목표

AI Coding Agent를 단순한 IDE 보조 기능이 아니라 저장소를 읽고, 명령을 실행하고, 코드를 변경하고, 결과를 검증하는 실행 주체로 바라볼 때 소프트웨어 프로젝트의 설계 전제가 어떻게 달라지는지 설명한다.

이 장에서는 특정 제품의 기능보다 이후 장 전체에서 사용할 문제 정의와 용어를 확정한다.

## 문제 정의

기존 프로젝트는 사람이 다음 정보를 암묵적으로 알고 있다는 전제에서 운영되는 경우가 많다.

- 어떤 문서를 먼저 읽어야 하는가
- 어떤 JDK와 빌드 도구를 써야 하는가
- 어떤 명령으로 실행하고 테스트하는가
- 어떤 외부 시스템이 필요한가
- 어떤 파일을 변경하면 안 되는가
- 작업이 완료됐는지 누가 판단하는가

사람은 경험과 대화를 통해 이 빈틈을 메울 수 있지만 Agent는 이 정보가 명시되지 않으면 탐색과 추론에 많은 context를 사용하거나 잘못된 결정을 내릴 수 있다.

## 핵심 주장

> AI Agent를 잘 사용하는 것보다 AI Agent가 잘 작업할 수 있는 프로젝트를 만드는 것이 더 중요하다.

AI Agent 시대의 프로젝트는 코드 저장소뿐 아니라 다음 기능을 제공하는 실행 가능한 작업 인터페이스가 되어야 한다.

- 발견 가능성
- 실행 가능성
- 테스트 가능성
- 검증 가능성
- 변경 경계
- 작업 상태

## 독자가 얻는 것

- Human-driven Development와 Agent-driven Development의 차이를 설명할 수 있다.
- 기존 프로젝트에서 Agent 작업을 방해하는 암묵적 의존성을 찾을 수 있다.
- `Repository as Interface`와 `Machine-verifiable Development`가 필요한 이유를 이해한다.
- 이후 장에서 사용할 `Agent Ready Software Engineering`의 범위를 이해한다.

## 예제 Stage

Stage 0 - 일반적인 Spring Boot 프로젝트

아직 Agent를 위한 별도 구조를 추가하지 않는다.

`campus-platform`을 Agent에게 처음 전달했을 때 발생하는 문제를 관찰하는 데 사용한다.

## 예제에서 보여줄 문제

- README에 실행 방법이 충분하지 않음
- 개발자 PC에만 존재하는 환경 설정
- 외부 DB가 없으면 테스트 실패
- 전체 검증 명령이 없음
- 모듈 경계와 변경 금지 영역이 불명확함
- 작업 완료 조건이 사람의 판단에 의존함

## 필요한 구조/그림

### 기존 개발 흐름

```text
Human
  ↓
IDE
  ↓
Code
  ↓
Build
  ↓
Test
  ↓
Deploy
```

### Agent가 참여하는 흐름

```text
Human / PM Agent
       ↓
Task
       ↓
Agent
       ↓
Repository
       ↓
Build / Test / Verification
       ↓
Result
```

### 핵심 변화

```text
사람이 알고 있는 프로젝트
        ↓
Repository가 설명하는 프로젝트
        ↓
기계적으로 실행하고 검증할 수 있는 프로젝트
```

## 필요한 코드 예제

이 장에서는 본격적인 구현 코드를 작성하지 않는다.

필요하면 잘못된 예시 수준으로 다음만 보여준다.

- 불완전한 README
- 개발자에게만 알려진 실행 명령
- 외부 DB 주소가 직접 박힌 설정

구체적인 개선 코드는 이후 장에서 단계적으로 추가한다.

## 필요한 공식 자료 조사

- Claude Code가 Repository와 명령 실행을 사용하는 기본 동작
- Codex 또는 다른 Coding Agent의 Repository 기반 작업 방식
- Cloud Agent의 격리 실행 환경 사례

제품별 세부 기능은 본문의 원칙을 설명하기 위한 사례로만 사용한다.
